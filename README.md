# Test-Driven Vehicle Control

A C-based vehicle driving and control simulation verified using requirements-derived, CSV-driven tests. The project includes unit tests, driving and control integration tests, requirement-linked testing, traceability consistency checks, and change impact analysis.

## Simulation

The program executes two stages in sequence:

1. **Driving simulation:** Read `simulation/command.csv` and `simulation/status.csv` row by row. Calculate engine state, gear, and speed, then update those three fields in `status.csv` while preserving sensor, door, and switch values.

2. **Vehicle control simulation:** Read the updated `status.csv`, monitor reception and sensor states, update timers, calculate vehicle-control outputs, and write `simulation/result.csv`.

### Driving Stage

`RunDrivingSimulation()` coordinates the following functions:

1. `ControlEngine()` — determine engine state from the command and current speed.

2. `ControlGear()` — determine gear from the command and current speed.

3. `UpdateVehicleSpeed()` — calculate speed from engine, gear, brake, and accelerator states.

4. `WriteVehicleStatus()` — write the updated status row.

The command and status files must have the same number of data rows with matching `timeMs` values. Invalid input or mismatched timestamps stop the stage. A temporary file is used so `status.csv` is replaced only after successful processing.

### Vehicle Control Stage

`RunControlSimulation()` processes each status row in this order:

1. `UpdateVehicleReception()` — update received signals and timeout states.

2. `MonitorVehicleState()` — check reception, speed validity, sensor faults, and warnings.

3. `UpdateVehicleTimers()` — update illuminance and wiper timers (skipped on the first cycle).

4. `UpdateVehicleControl()` — compute headlight, wiper, and door-lock states.

5. `WriteVehicleOutput()` — write control results to `result.csv`.

The four update/monitor helper functions are `static` in `vehicle_simulation.c`.

### State Data and Initial Conditions (C5)

The control stage separates three responsibilities:

| Structure | Responsibility |
| --- | --- |
| `VehicleStatus` | Current CSV input row, including missing-value markers |
| `VehicleReception` | Retained received values, last-reception timestamps, and individual `RxState` values |
| `VehicleMonitor` | Derived reception, validity, sensor fault, and warning states |
| `VehicleControlState` | Persistent control outputs and elapsed timers |

At startup, before processing the first status row, the simulation initializes the following states:

| State | Initial value |
| --- | --- |
| Engine | `ENGINE_OFF` |
| Gear | `GEAR_P` |
| Speed | `0` |
| Headlight | `HEADLIGHT_OFF` |
| Wiper | `WIPER_STOP` |
| Door lock | `DOOR_UNLOCKED` |
| Cluster warning | No warning (`CLUSTER_WARNING_NONE`, if defined under that name) |
| Low/high illuminance and wiper-active timers | `0` |
| Last-reception timestamps | `0` |
| Reception timeout flags | `RX_NORMAL` until the timeout threshold is reached |

Initial `RX_NORMAL` means "not timed out yet," not "already received." Initial stored illuminance/rainfall values are placeholders, not evidence of reception.

**C5 verification:** Initialization is part of the simulation lifecycle, so a dedicated integration test is more appropriate than reusing unrelated function-level test cases. The existing `test_control.py` compares processed CSV outputs and does **not** directly prove all pre-input initial states or timer values. A dedicated C5 initialization integration test has not yet been added; do not interpret passing unit tests or the first result row as full C5 verification.

### CSV Files

**Driver commands — `simulation/command.csv`:**

```csv
timeMs,engineCommand,gearCommand,brakeCommand,acceleratorCommand
```

Supported values include `ENGINE_CMD_OFF`/`ENGINE_CMD_ON`, `GEAR_CMD_P`/`GEAR_CMD_R`/`GEAR_CMD_N`/`GEAR_CMD_D`, and `PEDAL_RELEASED`/`PEDAL_PRESSED`.

**Vehicle status — `simulation/status.csv`:**

```csv
timeMs,speed,gear,engineState,illuminance,rainfall,doorFL,doorFR,doorRL,doorRR,lightSwitch,wiperSwitch
```

The driving stage updates `speed`, `gear`, and `engineState`; it preserves the other fields. **Running the simulator modifies `status.csv`.**

**Control results — `simulation/result.csv`:**

```csv
timeMs,headLightState,lightSensorState,wiperState,rainSensorState,doorLockState,clusterWarning
```

CSV enum values must match their C names exactly. Avoid spaces around field values in the current parser.

### Reception Timeout

Speed, gear, engine, illuminance, and rainfall reception are tracked independently. Missing inputs use the following symbolic values:

- Speed: `SPEED_NOT_RECEIVED`

- Gear: `GEAR_NOT_RECEIVED`

- Engine: `ENGINE_NOT_RECEIVED`
- Illuminance: `ILLUMINANCE_NOT_RECEIVED`
- Rainfall: `RAINFALL_NOT_RECEIVED`

`SPEED_NOT_RECEIVED`, `ILLUMINANCE_NOT_RECEIVED`, and `RAINFALL_NOT_RECEIVED` are defined as `INT_MIN` in `vehicle_types.h`. The CSV parser must recognize these symbolic values. The speed sentinel allows valid negative speeds (including `-1`) without confusing them with missing data. Sensor missing-value markers are distinct from actual out-of-range sensor readings.

Each received signal updates its last reception timestamp; `CheckReceptionTimeout()` reports `RX_TIMEOUT` when 500 ms or more have elapsed since the last reception. Before the first reception, the timeout is measured from simulation start (`timeMs = 0`). A newly received value clears the timeout.

The most recently received speed, gear, engine, illuminance, and rainfall values are retained when their corresponding signals are missing. Here, "received" does not necessarily mean "within the valid sensor range": an out-of-range sensor reading is still a received value and is evaluated as a fault.

Sensor fault detection (`C2`) uses both reception state and value range: illuminance must be between 0 and 60000, and rainfall between 0 and 100, inclusive. Timeout or an out-of-range reading produces `SENSOR_FAULT`; a newly received valid value restores `SENSOR_NORMAL`. The individual unit tests cover timeout and range decisions, but complete sensor-reception sequences still require integration verification.

## Build and Run

Requires GCC, Make, and Python 3 in a compatible host environment. The Makefile builds all `src/*.c` using `-Wall -Wextra -std=c11 -Iinclude`.

```bash
make          # Build vehicle_simulation
make run      # Build if necessary, then run both simulation stages
make clean    # Remove the executable
```

## Testing

### CSV-Driven Unit Tests

`test/test_unit.py` runs function-level tests from `test/testcases/<FunctionName>.csv`. Each test file contains a test case ID, function parameters in declaration order, and the expected return value in the final column.

```csv
testCaseId,parameter1,parameter2,FunctionName
```

Blank parameter cells represent **Don't Care** in the test specification; they should not be assumed to mean exhaustive input coverage.

```bash
make test-unit                       # All supported unit tests
make test-unit ControlWiper          # One function
make test-unit ControlEngine
make test-unit ControlGear
make test-unit UpdateVehicleSpeed
```

The suite covers driving, vehicle control, monitoring (including `CheckReceptionTimeout`), and timer functions.

### Driving Integration Test

`test/test_driving.py` compares **`simulation/status.csv` against `test/expected_status.csv`** using `timeMs` as the row identifier. It verifies the CSV columns, detects missing or unexpected timestamps, and compares all expected field values, including driving states and preserved sensor/switch inputs. Differences are reported per timestamp and field.

**This test does not compile or run the C simulator.** Generate an up-to-date status file first:

```bash
make run
make test-driving
```

A passing test reports `[PASS] timeMs=...` for each matching row and a summary of passed/failed rows. A mismatch produces a nonzero exit status.

The expected status CSV must correspond to the commands and initial sensor/switch inputs used for that simulation run. If `command.csv` or the test scenario changes, update `expected_status.csv` independently from the requirements. Avoid treating a stale `status.csv` as a fresh test result.

### Control Integration Test

`test/test_control.py` verifies vehicle-control outputs against the expected control results maintained in `test/expected_result.csv`.

```bash
make test-control
```

### Default Test Target

```bash
make test
```

With the updated Makefile, this invokes `test-unit`, `test-driving`, and `test-control`. The `test` target is not passed as a function argument to `test_unit.py`. Because `test-driving` compares existing CSV files, run `make run` first when you need to refresh the simulation outputs. Requirement-linked tests and traceability checks remain separate commands.

## Requirements and Traceability

`requirements/requirements.csv` defines requirements with these columns:

```csv
requirementId,category,description,priority,verification,precedence
```

`traceability/traceability.csv` links requirements to implementation functions and test cases:

```csv
requirementId,sourceFile,function,testFile,testCaseId
```

One requirement may map to multiple tests, and one test may support multiple requirements when the test directly verifies behavior shared by those requirements. For example, reception-timeout boundary tests can support both C2 and C4. Avoid linking C3 to timeout tests solely because speed validity consumes a reception status. Traceability supports review and impact analysis; it does not by itself establish complete verification coverage.

C5 initialization is currently implemented but not fully covered by a dedicated integration test or corresponding integration-test traceability entry. The current requirement runner is oriented around CSV-driven unit cases.

### Requirement-Based Testing

```bash
make test-requirement             # All mapped requirements
make test-requirement L1          # Specific requirement
make test-requirement W3
make test-requirement R1
```

### Change Impact Analysis

```bash
make analyze-impact D3
make analyze-impact W5
make analyze-impact R3
```

`test/analyze_impact.py` reports artifacts linked to the selected requirement. These are potential impacts identified through traceability, not automatic source-code change detection.

### Traceability Consistency

```bash
make check-traceability
```

Runs `test/check_traceability.py` to inspect consistency between requirements, implementation references, and test mappings.

## Scope and Limitations

Tests run on the host rather than an automotive MCU. Passing the defined cases does not demonstrate complete input-space coverage, structural code coverage, or production functional-safety compliance. The simulator updates `status.csv` via a temporary file, and the command/status inputs must remain synchronized. Both integration test scripts compare existing artifacts rather than independently executing the simulator. A dedicated pre-input initialization test is still needed for complete C5 verification; end-to-end reception timeout and recovery scenarios should also be tested.
